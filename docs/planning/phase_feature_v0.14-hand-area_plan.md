# 手札エリアの正式UI実装計画

## 開発範囲

- ブランチ: `feature/v0.14-hand-area`
- 予定バージョン: `0.14.0`。初回の実装開始時にpackage.jsonとpackage-lock.jsonを更新する。
- プレイヤー向け入口のレイアウトA/Bで、手札エリアだけを正式UIへ置き換える。
- 既存Cardを使用し、カード情報の確認、ステップ参照、拡大、プレイ操作を既存セッションへ接続する。
- 枚数に応じた配置・重なり、達成可能状態の表示を調整する。手札への出入りは状態を即時反映し、移動・裏返しなどの演出の追加・調整は対象外とする（実装中のオーナー指示による範囲変更）。
- バックログの実装順は手札、プレイ、パレット、ストック、デッキ、捨て札、情報表示とする。

## 表示方法の決め方

表示の細部はオーナーの意見を聞きながら段階的に決める。配置、重なり方、拡大時の挙動、達成可能状態の表示について具体案を提示し、意見を反映してから実装する。確認可能になった画面も提示し、調整を行う。重なったカードはタップして拡大する操作だけとし、選択による最前面への移動などは追加しない。

「4枚まで横並び、5枚以上は重ねる」は既存仕様の出発点であり、今回の確定デザインではない。担当者だけで細部を確定し、一括実装してから最終確認だけを依頼しない。既存仕様の変更が必要なら、要求仕様との整合性を確認し、合意した表示方法を実装仕様へ反映する。要求仕様は許可なく変更しない。

## 対象外

- 演出の追加・調整。オーナー指定により、全エリアの実装後に別途実施する。バックログの「全エリアの実装後に行う演出」で追跡する。

- 他6エリアの正式UIと演出。移動の接続に必要な変更は最小限とし、他エリアは仮表示を維持する。
- 3Dダイスのゲーム本体への組込みと、その際の容量・開始時間の改善。
- ゲームルール変更、過去記録の保存・比較、ランキング、アチーブメント、ギャラリー。
- 共通リポジトリGameWorksOAKの変更。

## 完了条件

- レイアウトA/Bの手札エリアで、割り当てられた論理寸法に合わせてカードを配置する。
- 手札0枚・少数・多数でも表示を維持し、重なったカードを含めて各カードの確認と許可されたプレイ操作ができる。
- ステップ参照や拡大だけではゲーム状態が変わらず、現在ステップを識別できる。
- 達成可能表示が現在の未使用ダイスに追従し、消費・破棄・リロール・面変更などを反映する。
- 選択待ちとプレイ条件は既存Gameに従い、UI独自の操作順序制限を追加しない。
- 手札への出入りを即時反映し、表示と操作対象がゲーム状態に一致する。移動演出・表裏のアニメーションと、それに伴う操作制御の検証は演出実装時に行う。
- リサイズ、A/B切替、パネル開閉、DPR変更で配置・操作・カード詳細の座標が崩れない。
- PC・タブレット・スマートフォン相当の画面で可読性と操作性を確認する。通常サイズでは全体スクロールを発生させず、オーナー合意の最低高さを下回る場合は、画面外の座標を保持するためレイアウト表示枠の縦スクロールを許可する。
- 評価用ゲームと開発者用画面を維持する。再描画・再プレイ・破棄時に監視やイベントを残さない。
- 合意した表示と必要なオーナー検証の判断・対応を実装報告へ記録する。
- 対象テスト、全テスト、本番ビルドとブラウザ確認を行い、結果を記録する。

## 実装方針

- `src/game/layoutPresentation.js`の手札ホストへ専用表示を接続し、既存Cardと共通アイコンを再利用する。
- `src/game/view.js`と`src/game/session.js`の操作受付・状態更新を使用し、ルールや達成判定を表示側に複製しない。
- エリア間移動ライブラリと画面レイアウト制御の論理座標・倍率を使用する。倍率を重複適用しない。
- 評価用配置とプレイヤー向け配置の責務を分け、共有する処理は共通化する。
- 配色・質感・形状・状態は既存共通UIとCSS規約に従う。新たな表示仕様はdocs/specへ記録する。
- 複雑な配置計算・状態管理は実装前にテストで仕様を定義する。

## 検証方針

- 対象テスト: 手札配置と選択、既存のカード・達成判定・セッション・エリア間移動に関係するテストを変更内容に応じて実行する。
- ブラウザ: A/B、枚数変化、重なったカードの選択、詳細表示、プレイ、ドロー・返却・仕事終了、選択待ち、達成可能表示、再プレイを確認する。
- 既存の`checkScreenLayout.cjs`、`checkGameConnection.cjs`、`checkIconCleanup.cjs`などを影響に応じて使用し、手札用の確認を補う。
- 実装終了草案前に`npm.cmd test`と`npm.cmd run build`を実行し、コマンド・結果・失敗時の調査結果を実装報告へ記録する。
- 表示の相談は実装中に段階的に行う。必要なオーナー検証は一意のID、理由、操作手順、期待結果、確認バージョンを添えて提示する。未回答を保留扱いせず、判断とフィードバックへの対応を記録する。
