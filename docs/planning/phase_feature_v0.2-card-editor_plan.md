# カード設定画面の開発計画

## 目的

ゲーム評価に先立ち、カード定義を編集し、JSONで保存・再読込できる道具を用意する。
後続のゲーム実装とバランス調整で利用できるよう、画面とデータの検証処理を分離する。

## 合意した範囲

- 予定バージョン: `0.2.0`。実装開始時にpackage.jsonとpackage-lock.jsonを更新する。
- ブランチ: `feature/v0.2-card-editor`。
- カード45枚の編集画面と、カードデータ形式を作成する。
- 「ゲーム設定を保存」でpublic/data/cards.jsonへ保存し、起動時は同ファイルから復元する。
- JSONダウンロード・取込は設けない。設定の取替えはpublic/data/cards.jsonの差し替えで行う。
- データはゲーム用の現在の構造に統一し、形式番号は持たせない。
- 不正な設定を検証し、問題の箇所と理由を表示する。
- 目標にAND／ORを指定でき、ANDを優先する。一覧ではANDを空白、ORを縦棒で表示する。
- 目標の達成確率を表示する。通常ダイスN個＋リロール1回を近似モデルで計算し、Nはグレード別に変更可能（A=4、B=5、C=6、保存不要）。

## 設定内容の確定方法

オーナーの指示により、どのような設定が必要かは実装時にオーナーへ質問して確定する。
計画への合意を、個々の設定項目やデータ形式への合意として扱わない。
回答を得る前に編集項目、達成目標の表現、効果の組合せ制約、必須値や既定値を確定しない。

実装時の相談の出発点は次のとおりとし、採用を確定した項目の一覧ではない。

- カードID、カード名、グレード、絵画画像の指定方法。
- ステップごとの達成目標と、色・画材・個数などの条件の表現。
- プレイ時効果・達成時効果の種類、パラメータ、複数効果の処理順。
- 未設定カードや制作途中のデータを保存できる範囲。
- 読み込み時の置換方法と、不正なデータを受け付ける範囲。

要求仕様との矛盾や今回のスコープの変更が必要になった場合は、オーナーへ相談する。
確認した設定要件は、実装時にゲーム側の仕様文書へ記録する。

## 対象外

- ゲーム進行、達成判定や効果のゲーム内での実行。
- カード45枚のバランス設計とプレイによるゲーム評価。
- 正式なゲームUI、アトリエ表現、物理ダイス、アニメーション、正式な効果アイコン。
- ランキング、アチーブメント、ギャラリー、公開設定。
- 共通リポジトリGameWorksOAKへの変更。
- エディターの狭い画面幅への対応。

## 完了条件

- 実装時に確認した要件に沿って、45枚のカード設定を編集できる。
- JSONに書き出した設定を読み込み、編集内容を復元できる。
- 確定した入力規則に反する設定を、箇所と理由が分かる形で検出できる。
- 起動時の設定読込に失敗した場合は、設定ファイルを初期値で上書きしない。
- 既存の仕様書・画像素材を保持し、設定画面で確認できるバージョンが設定値と一致する。
- 対象テスト、全テスト、本番ビルドを実行し、結果を実装報告へ記録する。
- 編集、保存、再読込をオーナーが検証できる状態にし、判断と対応を記録する。

## 実装・テスト方針

- 既存のViteとNode.jsのテスト環境を利用する。
- 編集画面、カードデータ、検証、JSON入出力の責務を分ける。
- 読み込むJSONを検証してから編集状態へ反映する。
- 複雑な検証・状態管理は、原則としてテストを先に作成する。
- 仕様テストはtests/spec/に要求仕様の章と対応して配置する。
- 実装テストはtests/implementation/にsrc/の構成と対応して配置する。
- JSONの往復による内容保持、不正データ、読込失敗時の状態保持を検証する。
- PCブラウザで編集・ゲーム設定保存・再読込の実操作を確認する。
- 実装終了草案の提示前にnpm.cmd testとnpm.cmd run buildを実行する。
- オーナー検証は一意のID、操作手順、期待結果、確認バージョンを添えて提示する。
