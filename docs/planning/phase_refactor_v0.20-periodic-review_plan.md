# v0.20 定期見直し計画

## 合意内容

- 終了草案へのオーナー指摘で、キーボード操作は要求しておらず元の仕様を正とすることが確認された。実装修正時は共通のPatch更新規定に従い0.20.1とする。
- 開発ブランチ: `refactor/v0.20-periodic-review`
- 予定バージョン: `0.20.0`。初回の実装開始時に `package.json` と `package-lock.json` を更新する。計画中は `0.19.1` を維持する。
- 共通ワークフローの10回ごとの定期見直しとして、文書とソースの点検・整理を行う。
- フェーズ開始と、本計画のスコープ・完了条件・予定バージョン・ブランチ名について、それぞれオーナーの合意を得ている。

## 開発スコープ

### 開発ルールと文書

- 共通のワークフロー、フェーズ作業手順、文書・コード・CSSの規約と、ゲーム固有の規定を再確認する。
- `docs/01.development.md`、`docs/spec/`、`docs/planning/backlog.md` を現行実装と照合する。存在しない仕様・参照先、古い操作説明、責務や章構成の不整合を修正する。
- `docs/requirements/` は照合用に読む。要求仕様そのものは変更しない。
- 文書は意味の区切りと参照の明確さを優先し、必要な場合だけ分割する。

### ソース

- `src/`、`scripts/`、起動HTMLとビルド・保存APIの設定を点検し、未使用コード、重複、文書との不整合、ファイルサイズを確認する。
- 動作を維持する整理に限定する。分割・移動は責務と依存関係を確認し、必要な箇所だけ行う。
- 行数は空行を含む実際の行数で確認する。共通コード規約の1ファイル500行制限と照合する。

### テストとブラウザー検証

- 要求仕様の挙動と `tests/spec/` の検証対象を照合し、既存の未検証範囲を明確にする。
- `tests/implementation/` の責務・配置と対応ソースを照合する。ソースを分割・移動する場合は関連テストも整理する。
- `scripts/checkPaletteArea.cjs` のTab移動チェックを、元のTab対象外仕様と整合させる。単に検証を削除したり、すべてのTab移動を無条件に許容したりせず、対象と期待値を明示する。
- オーナーの訂正指示に従い、元の仕様を正とする。効果説明アイコンも `tabIndex=-1` とし、Enter／Space／Escapeによる開閉処理を削除する。ホバー・クリック・タップ操作は維持し、元の操作仕様へ実装を合わせる。

### バックログ

- 要望・バグ指摘の依存関係・優先順、部分対応の残作業を確認する。
- オーナー検証は、利用者が操作・確認できる単位と一意のIDで判断できるか確認する。未回答を保留として追加しない。
- 点検で見つかった範囲外の不具合や新規作業は、根拠と残作業を示して要望・バグ指摘へ記録する。

## 対象外

- デッキ・捨て札・情報表示の正式UI実装、効果ごとの正式UI実装。
- 新機能、ゲームルール・要求仕様・操作仕様の変更、見た目や演出の刷新。
- 見直しに必要のない広範囲の再設計や、一律のファイル分割・テスト追加。
- 隣接する `GameWorksOAK` リポジトリの編集。共通部に問題があればオーナーへ報告する。
- 公開環境、CI、ポータル登録の新設。

## 計画時点の確認事項

- 開始時は `master`、引継ぎ書なし。直前はストック正式UIのマージで、設定バージョンは `0.19.1`。
- バックログでは正式UIの次対象がデッキだが、今回のMinorは定期見直しを優先する。
- `checkPaletteArea.cjs` は操作要素のTab移動対象をゼロと期待する一方、開始時の `iconPopovers.js` は説明アイコンに `role=button` と `tabIndex=0` を設定していた。オーナーが元のTab対象外仕様を正と確認したため、実装側の不整合を修正する。
- 計画時の構成確認は点検対象の特定であり、全ファイルの適合や未使用コードの不存在を保証するものではない。

## 実装方針

1. 変更前のテスト・ビルド結果を確認し、文書、ソース、テスト、バックログごとの点検記録を作成する。
2. 発見事項を今回整理するものと範囲外のものに分け、理由を記録する。動作変更が必要になる場合は独断で範囲を広げず、オーナーへ相談する。
3. 文書・コード・テストを必要最小限で整理し、関連する検証を実施する。複雑なロジック変更が必要なら共通規約のTDD方針に従う。
4. 全テストと本番ビルドを実行し、失敗は原因と今回の変更との関係を調査する。
5. 実装報告に点検範囲、判断、変更、検証結果、範囲外の発見事項、オーナー検証の扱いを記録する。

## 検証方針

- 対象テスト: 変更したモジュールに対応する既存テストを実行する。配置を整理する場合は移動後の検出と参照も確認する。
- Tab移動チェック: `node scripts/checkPaletteArea.cjs <開発URL>` を実行する。必要に応じて `checkEffectCommonUi.cjs` も使用し、説明アイコンのキーボード操作を検証する。
- 開発URLは `npm.cmd run dev -- --host 127.0.0.1` で起動した実際のURLを使用する。外部Playwrightは既存の環境変数による指定を使用し、必須依存へ追加しない。
- 整理した機能に応じてゲーム起動・レイアウトA/B・開発者画面の既存検証を選ぶ。共通規約のモバイル要件に関係する整理では狭い画面とリサイズも確認する。
- 全テスト: `npm.cmd test`。
- 本番ビルド: `npm.cmd run build`。
- 対象テスト、全テスト、ビルドのコマンドと結果を実装報告へ記録する。既存失敗でも省略せず、調査結果と今回修正しない理由を記録する。
- 要求仕様とテストに矛盾があれば、テストを都合よく変更せずオーナーへ確認する。

## 完了条件

- 開発ルール・文書・ソース・テスト・バックログの各点検範囲、判断、修正内容が実装報告から追跡できる。
- 必要な文書参照・実装記述と、ソース・テストの責務や配置が整合する。残る事項は理由と残作業を記録する。
- パレットのTab移動チェックが、効果説明アイコンを含めた元のTab対象外仕様と整合し、対象ブラウザー検証で結果を確認できる。
- 新機能・仕様変更を混在させず、範囲外の発見事項がバックログに記録されている。
- 対象テスト、全テスト、本番ビルドを実施し、結果と失敗調査が記録されている。
- オーナー判断が必要な項目が生じた場合は、一意のID・理由・手順・期待結果・確認バージョンを提示し、判断と対応を記録する。未回答・未対応のまま終了草案を提示しない。
- 実装結果と次フェーズをレビューとする引継ぎ草案を提示し、承認後に保存・終了コミットする。
