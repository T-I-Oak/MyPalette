# 効果発生時の共通通知と説明文 計画

## 合意内容

- 対象: EUI-C01「効果発生時の共通UI」と、ユーザー向け効果説明文の確定・共用。
- 予定バージョン: 0.17.0。初回実装開始時にpackage.jsonとpackage-lock.jsonを更新する。
- ブランチ: feature/v0.17-effect-common-ui（作成済み）。
- 効果を得たとき、何を得たかを画面中央付近へ一時表示する。獲得以外の変更・破棄も対象とする。
- 通知はカードのプレイ時・達成時効果ボックスに似たスタイルを使う。
- 発動契機アイコンと外枠は一体。左の背景色付きアイコン欄を1つ設け、縦の仕切り線の右に本文を置く。
- 複数効果は同じ枠の本文に「効果アイコン＋説明文」を複数行で表示する。発動契機アイコンを各行へ繰り返さない。効果ごとに別通知として順に表示する旧案は撤回する。
- カードの効果アイコンのホバー表示にも、通知本文と同じ「効果アイコン＋説明文」を使う。
- 説明文の時制切替は必須としない。共用文を基本とし、通知であることを伝えるタイトルが必要なら「効果を獲得しました」等を本文とは別に検討する。タイトルのために発動契機アイコンを独立した見出しへ変更しない。
- 確認ボタンは設けず自動で消す。既存の対象選択と物理ロールを使う。
- 説明文の整理に際し、現在の効果分類が実装を煩雑にする場合は再分類も検討する。再分類する場合は仕様・カード定義・実装・開発者用ツールへ漏れなく反映する。
- アイコンの図柄・見た目は変更しない。再分類が必要な場合も既存アイコンを使用し、分類・パラメータから既存アイコンへの対応付けだけを必要に応じて更新する。

## デザイン確認の根拠

src/game/Card.jsのblock関数はPaintingBlock内にPaintingBlockLabelと本文を配置する。発動契機のSVGはラベル欄に含まれる。src/game/card.cssではラベル欄に背景色と右側の仕切り線を付け、外枠と一体化している。プレイ時はplayの青系、達成時はrewardの緑系の共通UI変数を使う。通知でもこの構造・図柄・色の対応を引き継ぐ。

カードでは本文の効果アイコンが横並びだが、通知では本文だけを効果ごとの複数行へ拡張する。カード自体の配置・寸法・本文の横並びは変更しない。

実画面への接続はComputer UseのURL判定エラーで中断した。コードで確認した上記構成をチャットで説明し、オーナーから「デザインの認識はあっています」と確認を得た。実画面を確認済みとは扱わない。

## スコープ

### ユーザー向け説明文

現在の「効果名・一時・×1」等のパラメータ列挙を、そのまま利用者へ提示しない。全16種類について、数量、永続／一時、補色、画材、変更先ステップ、名声の増減、特殊面の種類などの設定値を含む説明文のテンプレートと用語を整理する。要求仕様と実装を照合し、対象・操作・獲得先など判断に必要な意味が伝わる文章とする。

実装に先立ち文言案を一覧で提示し、オーナーと確定する。通知とカードの効果ホバーで同一の本文描画・説明文生成を共用する。既存の日本語・英語の翻訳経路を維持し、日本語の合意内容と英語の意味を揃える。開発者用の設定ラベル・ログを一律に書き換える作業は含めない。

### 効果分類の見直し

現在の16種類を固定の制約とせず、説明文とパラメータの関係、処理の共通性、開発者用ツールでの設定のしやすさを点検する。再分類が有効な場合は、変更理由、新旧分類とパラメータの対応、ゲーム上の意味を維持できること、影響先と移行方針をオーナーへ提示して合意を得る。説明文は必要に応じて再分類後の全種類について確定する。

再分類を行う場合は、要求仕様・実装仕様、保存済みカード定義、効果カタログ・検証・処理・既存アイコンへの対応付け・説明文、開発者用のカード設定・評価・保存読込、関連テスト・補助スクリプト・文書を調査し、一貫して更新する。アイコン自体の図柄・見た目は維持する。dev-dataの評価メタデータや特殊面との対応も確認する。既存定義の移行と保存・再読込・ゲーム起動まで確認し、旧分類への参照の取り残しを検索する。互換性対応の要否と、不明な旧定義を黙って補完しない方針を具体化する。

本件に必要な仕様・カード定義・開発者用ツールの変更はスコープに含む。再分類に伴う要求仕様の変更も今回のオーナー指示に基づく範囲とし、ゲームルールそのものの変更は含めない。再分類の有無と判断理由、影響先ごとの対応結果を実装報告へ記録する。

### 共通通知

プレイ時・達成時の効果を発動契機ごとにまとめ、同じ枠内に全効果のアイコンと説明文を複数行で表示する。プレイ時は着手演出後、達成時はカード・イーゼル撤去後に提示する。枠と左のアイコン欄は効果数にかかわらず1つとする。

通知は効果の内容を伝える共用文を基本とするため、未確定の選択結果や設定数を実際の取得済み結果として断言しない。選択・ロールを要する場合の表示開始・消去タイミング、対象なし・数量不足、特殊面による入れ子のまとめ方は、既存処理と整合する具体案を実装前に提示する。旧案の「全効果を解決後に実績値だけを1件ずつ通知する」方式は前提としない。

同一更新内の複数発動を落とさず、再描画で重複しない仕組みを設ける。日次の予約効果など同じ効果経路を通る場合の扱いを整理する。通常の日次ドロー・権利付与など進行全体の通知拡張は対象外とする。

## 対象外

- 個別バックログEUI-01〜EUI-16の選択UI・固有演出の正式化。確認済みEUI-06の操作刷新。
- 残る4エリアの正式化、仮エリアとの移動演出、長押しによるダイス情報表示。
- ホバー全般の操作・位置・タイミング改善。本開発では効果ホバーの本文形式と説明文を扱い、既存の別バックログは残す。
- カード本体のデザイン変更、目標ホバーの刷新。
- 効果アイコンおよび発動契機アイコンの図柄・見た目の変更。
- ゲームルールの変更とGameWorksOAKの変更。要求仕様・保存済みカード定義は、合意した再分類に必要な場合に限り変更対象とする。
- 処理順・待機状態を一覧するパネル、通知確認ボタン、過去通知の閲覧機能。

## 完了条件

1. 全16効果と各パラメータに対応するユーザー向け説明文案を提示し、オーナー合意を記録して反映する。
2. 通知の枠・発動契機アイコン欄が既存カードと対応し、複数効果が同じ本文内の複数行で表示される。
3. 通知とカードの効果ホバーで「効果アイコン＋説明文」を共用し、意味・用語が一致する。
4. 通知は中央付近に一時表示され、自動で消える。既存の選択・即時リロール・物理ロールを妨げず、操作の二重実行を起こさない。
5. 着手・達成演出との順序を守り、連続発動・選択待ち・ロール待ち・対象なし・不足・入れ子で通知が欠落・重複せず、誤った獲得結果を断言しない。
6. 再プレイ・画面破棄で通知とタイマーを解放する。A/B、リサイズ、固定倍率変更で読みやすさを維持し、動きを減らす設定でも内容を確認できる。
7. 段階的なオーナー検証と対応を記録し、対象テスト・全テスト・本番ビルドのコマンドと結果を実装報告へ記載する。
8. 効果分類を点検し、再分類する場合は新旧対応と移行方針の合意を得て、仕様・カード定義・実装・開発者用ツール・関連テストへ漏れなく反映する。ゲーム上の意味を維持し、保存・再読込・ゲーム起動と旧参照の取り残しを検証する。

## 実装・テスト方針

- Generator、pending、rollRequest、既存の演出接続と操作契約を再利用し、通知のためにゲームルールや効果処理順を変更しない。
- 発動契機・効果配列の構造化データを使う。ログの文字列を解析しない。描画更新から通知の寿命・重複防止を切り離す。
- カードの枠・SVG・配色と効果本文を共用できる部品へ整理し、描画資源の解放を維持する。
- cardMessages.jsのユーザー向け説明生成とcardIcons.jsの現在文字だけのツールチップを主な接続箇所とする。開発用cardSummary.jsの責務と混同しない。
- docs/specへ通知構造・説明文契約・ライフサイクルを記録し、バックログでは共通通知と個別効果UI・ホバー全般の残作業を区別する。
- 複雑な状態管理はテストを先に定義する。説明文のパラメータ分岐、複数効果のまとめ、選択・ロール前後、入れ子、重複防止、破棄を検証する。
- 既存の進行・効果・カード・達成演出を回帰確認し、ブラウザで表示と操作を確認する。
- 実装終了草案前に npm.cmd test と npm.cmd run build を実行する。

## オーナー確認の順序

1. 現在の効果分類を点検し、必要なら再分類案と移行方針を提示して合意を得る。その分類に基づく全効果の説明文案と、未確定の通知タイミング等の具体案を提示して合意を得る。
2. 単一効果と複数効果の通知、同じ本文のホバー表示を小さな実装で提示し、配置・大きさ・表示時間を確認する。
3. 残る効果と中断・再開へ接続し、操作手順と期待結果を提示する。
4. 各検証に一意のID、理由、手順、期待結果、設定と一致する確認バージョンを付け、判断と対応を記録する。未回答を保留扱いしない。
