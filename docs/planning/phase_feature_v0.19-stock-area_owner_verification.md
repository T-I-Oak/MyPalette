# ストックUIのオーナー検証記録

## 記録の根拠と読み方

- SR-01への対応として、実装担当とオーナーのこのチャットの会話を照合した。
- 0.19.0での提示時には検証IDを付けていなかった。以下のSV-01〜SV-07は0.19.1の記録整理時に付与したIDであり、当時ID付きで提示したという意味ではない。
- 確認対象の実装バージョンはすべて0.19.0。今回の0.19.1は記録とバージョンの更新のみで、機能・演出は変更していない。
- 手順は、当時の提示内容・操作フローを整理して記載した再現手順であり、当時のチャットに以下の文章をそのまま提示したという意味ではない。根拠となる発言も別記する。
- 案への合意、修正指示、実装結果への判断、フェーズ終了承認を分けて記録する。確認済み項目の再検証は依頼していない。

## SV-01 表示・配置・グレード文字

- 確認が必要な理由: 仮表示から正式UIへの変更で、余白・間隔・文字の所属層をオーナーと決める必要があった。
- 提示: 0.19.0の正式表示案を実装して通常入口`http://127.0.0.1:3005/MyPalette/`を案内。その後、グレードを拡縮層に置く試案と文字の拡大を実装して同じ入口を再提示した。
- 操作手順: 通常入口を開き、A/Bでストック3列、グレード・枚数、余白を確認し、公開カードをタップして詳細を開く。
- 期待結果: A/B/Cを識別でき、公開・裏面と枚数が一致する。空の山も列位置を維持し、「公開カードなし」は出さない。背景は透明、山間隔は広がりすぎず、グレード・枚数はカードと同じ倍率で表示される。
- 判断の根拠: 「背景は消してください」「横幅に余裕があるときに離すのはいいですが、離しすぎは良くない」、拡縮層を試す指示、「もっとカード幅いっぱいに描いた方が良い」に対応して再提示。その後の「いったんこれで行きましょう」を表示試案の採用判断として記録する。
- 対応結果: 背景透明、山間隔32〜64、拡縮層の文字40px/48pxを採用。詳細タップは既存部品を再利用。下端余白の後続修正はSV-07に記録する。
- 判断: 表示試案を採用。詳細表示単独について別の目視承認があったとは記録しない。自動検証結果は実装報告に記録。

## SV-02 初日配分・朝の公開・日末更新

- 確認が必要な理由: 状態変化のタイミングと、物理的なカードの扱いをオーナー指定へ合わせるため。
- 提示: 「0.19.0で実装しました」として、初期各15枚裏面、初日Aから7枚をデッキへ移動後に公開、日末の裏返し・最下段差し込み、翌朝公開を説明し、通常入口を案内した。
- 操作手順: 初期状態を確認し、「今日の仕事を始める」を押す。初日の配分・公開を見て、日末に仕事を終え、翌日の仕事を開始する。
- 期待結果: 初期は各15枚裏面。初日開始時にAから7枚がデッキへ移動後、各先頭が公開される。公開は持ち上げ・縦軸回転・復帰。日末は裏返し・左へカード幅移動・下降・最下段差し込みとなり、他カードは1.5上へ移動。翌朝まで先頭も裏面。A/B/Cの開始は少しずれる。
- 案・仕様への指示: オーナー自身が初期・朝・日末の流れと縦軸回転・左へ抜く動きを説明し、「シームレスに移動することを重視」と指定。「A, B, Cのアニメーションを少しずらす」指示も実装した。これらは仕様の根拠であり、実装結果の確認済みとは当時記録しない。
- 過去の結果判断: 個別の確認済み回答を特定できなかった。実装後の「作業を進めてください」を、この項目の目視承認へ読み替えない。
- 今回の判断: 0.19.1のSR-01対応中、SV-02・SV-04・SV-05の判断を質問したところ、オーナーが「3項目とも確認済み」と回答。確認対象は旧版0.19.0。今回得た確認済み判断として記録し、過去の承認を作らない。
- 対応結果: 指定の流れと演出を実装済み。要求仕様の従来の初期準備・日末公開との記述差はオーナー指定に由来し、実装仕様へ記録。要求仕様自体は未変更。

## SV-03 初日配分時の前後関係

- 確認が必要な理由: 出発前のカードを前面へ出す実装が、山の物理的な積み順を崩していた。
- 提示・指摘: オーナーが配分カードと山のz-indexを質問。担当が出発前から50〜56・公開予定カードに80を設定している問題を説明し、オーナーが「不適切ですね」と指摘した。
- 操作手順: 初日の仕事を開始し、Aの上から7枚を抜くときの重なり順を見る。
- 期待結果: 出発前のカードと公開待ちのカードは元の積み順。出発したカードだけが山の手前へ移り、同時移動中も元の上下関係を保つ。
- 再提示: 修正後に「出発前は元の積み順を維持」「出発したカードだけを山より手前」「公開カードも持ち上げ開始まで前面へ出さない」と説明し、テスト・ブラウザー検証・ビルド成功を報告した。
- 判断: この修正報告の直後にオーナーが「ok」と回答。0.19.0の修正結果を確認済みとして記録。今回の再検証依頼は行わない。

## SV-04 ストック上の取得操作・補充・Bパネル

- 確認が必要な理由: 発注・効果・交換の取得を、仮ダイアログから正式ストックの操作へ置き換えるため。
- 案への合意: 各山の下部固定倍率層の「取得」、カードタップで詳細、Bの選択待ちでパネルを開く案に「この案で進める」と回答。これは当時の案への合意として記録する。
- 提示: 0.19.0で取得ボタン・B自動表示・連続取得・補充公開・最後の発注から日末への連鎖を実装し、通常入口で取得ボタンと補充の確認を依頼した。
- 操作手順: 発注・カード効果・手札交換で取得待ちに進み、対象の山の下の「取得」を押す。連続取得では次の公開カードを選び、Bではパネルが開くことを見る。
- 期待結果: 取得可能な山だけにボタンが出て、ゲームの選択制約に従う。取得先と枚数が更新され、次の先頭が補充公開される。進行停止中は有効なボタンに注目状態が付く。
- 過去の結果判断: 案への合意と、以後のz-index質問を、この機能全体の目視承認へ読み替えない。
- 今回の判断: SV-02と同じ質問に「3項目とも確認済み」と回答。0.19.0の実装結果について今回得た確認済み判断として記録する。
- 対応結果: ストック用ダイアログを置き換え、取得・補充・B自動表示と注目状態を実装済み。ボタン中心の修正はSV-06に記録する。

## SV-05 正式な手札返却選択・手札との往復移動

- 確認が必要な理由: 手札交換の返却・取得も正式UIと連続した移動に接続するため。
- 案への合意と追加指示: 返却の持ち上げ・裏返し・山の左から最下段への差し込み、取得の持ち上げ・手札への移動・補充の案に「この案で進める」と回答。その後、オーナーが「ダイアログは仮UI」「手札の下部のボタンで選択するのが正式」と指定。進行停止中の選択ボタンへの注目属性も指定した。
- 提示: 0.19.0で手札下部の返却ボタンと往復移動を実装して確認を案内。発動しづらいという回答を受け、`http://127.0.0.1:3005/MyPalette/tmp_stock_review.html`を生成し、「仕事開始→任意の手札で着手→返却→取得」の手順を提示した。
- 操作手順: 確認ページで仕事を開始し、任意の手札に着手。手札下部の「返却」を押し、移動後にストック下部の「取得」を押す。
- 期待結果: 返却は仮ダイアログを使わず正式ボタンで選択。有効な選択ボタンが注目表示。返却カードは裏面で山の最下段へ入り、取得カードは手札へ移動後に補充公開される。残る手札の位置も連続して変わる。
- 過去の結果判断: 確認ページでの2点の指摘と修正後のokはSV-06・SV-07に対応する。これを往復移動全体の個別承認へ拡張しない。
- 今回の判断: SV-02と同じ質問に「3項目とも確認済み」と回答。0.19.0の実装結果について今回得た確認済み判断として記録する。
- 対応結果: 正式返却選択、注目状態、往復移動・補充を実装済み。確認ページは設定のコピーだけを変更し、保存済み設定には影響しない。

## SV-06 取得ボタンの注目拡縮の中心

- 確認が必要な理由: 確認ページで「取得ボタンの注目での拡縮の起点が中央になっていません」と指摘された。
- 操作手順: 確認ページで返却後の取得待ちに進み、「取得」の注目アニメーションを見る。
- 期待結果: ボタンの見た目の中心を変えずに拡縮する。
- 再提示と対応: 中央寄せをボタン外側のStockAcquireSlotへ分離し、ボタン自身は拡縮だけを行うよう修正。「2点とも修正しました」と確認ページの再読み込みを案内した。
- 判断の根拠: オーナーが「両方とも原因を教えてください」と質問。担当がボタン自身のtranslateXとscaleの重なりを説明した後に「ok」と回答。0.19.0の当該修正結果を確認済みとして記録。今回の再検証依頼は行わない。

## SV-07 通常時と交換中の山の下端

- 確認が必要な理由: 同じ確認ページで「山の下の方が見切れているかもしれません」「交換中だけ山の下の方が見える」と指摘された。
- 操作手順: 交換前と交換中で、山の下端・裏面・影の見え方を比べる。
- 期待結果: 層が変わってもカードの寸法が変わらず、通常時も下端の影が切れない。
- 再提示と対応: 移動層のカードもborder-boxに統一し、下端の影用余白を22へ拡大。SV-06とまとめて修正結果を提示し、確認ページの再読み込みを案内した。
- 判断の根拠: 「両方とも原因を教えてください」に対して、通常時と移動時の寸法計算の差と影の余白不足を説明。その後の「ok」を2点の修正に対する確認済み判断として記録する。今回の再検証依頼は行わない。

## フェーズ終了承認との区別

- 0.19.0では全195件のテスト・ビルド・ブラウザー検証の報告と、次をレビューとする引継ぎ草案を提示し、オーナーの「ok」で承認された。
- これは当時の引継ぎ草案への承認として記録する。SV-02・SV-04・SV-05の当時の個別目視判断があったという根拠にはしない。
- 0.19.1の記録整理でSV-02・SV-04・SV-05の確認済み判断を今回得た。オーナーが現時点では確認しないと指定した項目はなく、保留としてバックログへ移す項目はない。
