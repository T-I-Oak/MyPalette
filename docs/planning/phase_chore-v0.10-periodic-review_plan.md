# v0.10.0 定期見直し計画

## 目的

共通ワークフローで Minor の下1桁が0になる版に定められた定期見直しを行い、My Palette の開発手順、文書、テスト、ソースの整合性を確認する。

- 予定バージョンは `0.10.0`。実装フェーズ開始時に `package.json` と `package-lock.json` を更新する。
- 開発ブランチは `chore/v0.10-periodic-review`。

## 開発範囲

| 対象 | 点検する内容 |
| --- | --- |
| 開発ルール | GameWorksOAK の共通規約と `docs/01.development.md` を照合し、フェーズ手順とプロジェクト固有の手順の整合性を確認する。 |
| 文書 | `docs/spec/` の仕様の不足、章構成、リンク・参照先を現行実装と照合する。 |
| テスト | `tests/spec/` と要求仕様、`tests/implementation/` と実装の対応を確認する。ソースを分割・移動した場合は関連テストの責務と配置も見直す。 |
| ソース | `src/` の未使用コード、文書との整合性、共通規約の1ファイル500行制限を確認する。 |
| バックログ | 要望・バグ指摘の依存関係と優先順を確認する。オーナー検証項目がある場合は、利用者が操作して個別に判定できる単位かを確認する。 |

現行の挙動を保ったまま修正できる不整合を整理する。点検で見つかった機能上の不具合や仕様変更が必要な項目は、既存項目との重複を確認し、バックログの「要望・バグ指摘」に記録する。

## 対象外

- チラシによる発注でカードを取得する際の名声条件の変更。
- プレイヤー向け UI や追加機能の実装。
- `docs/requirements/` のゲーム要求仕様の変更。

## 実装・検証方針

1. 対象ごとに点検し、根拠となる規約、文書、ソース、テストを照合する。
2. 点検結果に基づいて必要な箇所を整理する。ソースを変更した場合は、関連する対象テストを実行する。
3. 実装終了の引継ぎ草案を提示する前に、リポジトリ直下で `npm.cmd test` と `npm.cmd run build` を実行する。失敗した場合は原因を調査し、今回の変更に起因するものは修正して再実行する。
4. 点検範囲、修正内容、残課題、実行した検証コマンドと結果を実装報告に記録する。

## 完了条件

- 開発範囲の5項目を点検し、修正内容と残課題を実装報告で確認できる。
- 全テストと本番ビルドが成功する。
