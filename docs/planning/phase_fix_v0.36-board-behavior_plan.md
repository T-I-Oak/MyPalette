# コルクボードの自動クローズと非表示時の演出省略

## 合意内容

- 開発ブランチ: `fix/v0.36-board-behavior`
- 予定バージョン: `0.36.0`。実装開始時に package.json と package-lock.json を更新する。計画では現行 `0.35.1` を維持する。
- オーナーは計画フェーズ開始、続いて以下のスコープ・方針・バージョン・ブランチ名に合意した。
- 対応バックログ: 「ストック獲得のため自動で開いたコルクボードを獲得後に閉じる」「レイアウトBでコルクボードを閉じている間はボード上の演出を省略する」。後者には初日の7枚配分を追加する。

## スコープと動作

### 取得後の自動クローズ

- レイアウトBで、ストック取得または手札交換のために閉じたボードを自動で開いた場合、一連の取得・補充演出が終わってから閉じる。発注による取得も対象にする。
- 連続取得・交換では、次の取得・返却を含む一連の操作終了まで開いたままにする。通知・移動待ちや再描画を操作終了と誤認しない。
- 手動で開いていたボードは閉じない。自動で開いた後、一度でもユーザーが開閉した場合、その一連の操作では自動クローズの対象から外し、手動の開閉を優先する。閉じて再び開いた場合も取得後は開いたままにする。
- 同じ選択要求の再描画では開き直さない。連続処理内で手動操作を自動開閉によって上書きしない。
- ゲーム終了・タイトル復帰・新しい局に前の取得処理の管理状態を持ち越さない。

### 閉じたボード内の演出省略

基準は「レイアウトBで閉じているとき、ボード内だけで完結するカード演出を省略する」。以下を対象にする。

1. ストック公開カードの切り替え。裏返し・最下段への挿入・次カードの公開、初日や翌朝の公開、取得後の補充公開を含む。
2. 捨て札からデッキへの再構成。広げる・集める・デッキへ移す全段階を含む。
3. 初日のストックAからデッキへの7枚配分。デッキから手札へのドローとは区別する。

- 各演出の開始時点で省略を判定する。開始時に開いていれば、その演出は途中で閉じても最後まで続ける。閉じていれば最終状態へ即時更新し、途中で開いても省略済みの演出を再生しない。
- 複数段階で一つの対象演出を構成する場合は、開始時の判定を全段階で共通にする。ストックの切り替えや再構成の途中で方針が変わらないようにする。
- 閉じるスライドの途中は「閉じている」に含めず、完全に閉じた状態を省略対象とする。開閉の目標値だけで非表示と判断しない。
- 省略してもゲーム処理と表示の更新、カードの所属・順序・表裏・枚数、再構成のシャッフルと再開処理を維持する。開いた際は更新後の状態を表示する。
- 開いている場合とレイアウトAでは既存演出を維持する。動きを減らす設定による既存の即時更新も維持する。
- A/B切替時は現在のレイアウトで新たな演出の省略を判定する。取得処理中の切替で手動状態の保持や選択継続を壊さず、A上で不要なクローズ操作を発生させない。

## 対象外

- デッキ→手札のドロー、手札→ストックの返却、ストック→手札の取得、手札・プレイエリア→捨て札の回収など、メイン側につながる移動演出の省略。
- 効果UIの正式化、その他のバックログ、MP28-02の原因調査。
- 共通リポジトリの編集、要求仕様の無断変更、保存済みカード設定の変更。

## 現在の実装と実装方針

- `src/ui/screenLayout/createLayoutScreen.js` がレイアウト・開閉目標・スライド進捗を保持する。現在の公開APIは `openPanel()` のみ。レイアウトと開閉状態の参照、自動開閉と手動開閉の区別をここに集約し、利用側で別々の真偽値を持って食い違わせない。
- `src/game/layoutPresentation.js` は取得・返却の選択が操作可能になった際にボードを開く。選択要求の変化と、一連の取得・交換処理の終了を区別して自動開閉を管理する。
- `src/game/cardSceneTimeline.js` が配分、公開・切り替え、再構成、取得・返却を順序制御する。対象演出だけを即時更新し、ゲーム進行や後続演出を飛ばさない。再構成の再開コールバックは一度だけ実行する。
- 複雑な状態制御は、先に意味のある状態遷移テストを作成して実装する。必要なら小さな管理モジュールへ分割し、共通の座標変換と既存カード個体の管理を再利用する。
- `docs/spec/14.screen_layout.md`、`docs/spec/18.card_scene.md` と開発・検証案内を実装に合わせて更新する。バックログの完了項目削除はレビュー承認後に行う。

## 完了条件と検証方針

1. 通常取得、発注、手札交換、連続取得・交換で、自動開閉と手動優先が上記のとおり動作する。対象なしで無用な開閉や待機を発生させない。
2. 対象3種類はBの完全な閉状態で待ち時間なく最終状態へ更新され、開状態とAでは従来の演出を再生する。
3. 演出中の開閉、取得中の手動開閉、A/B切替、リサイズ、固定倍率変更、動きを減らす設定で、選択・表示・カード所属に不整合がない。
4. 初日配分後の手札ドロー、取得・補充後の後続効果、再構成後のドローが正しい順序で続き、取消・終了・再開始に管理状態を持ち越さない。
5. 対象の状態遷移テストとブラウザー検証、全テスト、本番ビルドが成功する。失敗があれば共通手順に従って調査・記録する。

対象テストは新設または既存の `tests/implementation/ui/screenLayout/`、`tests/implementation/game/` に責務に沿って配置する。ブラウザー検証はボード操作用の検証を用意し、既存の `checkStockAcquisition.cjs`、`checkStockEdgeCases.cjs`、`checkStockDiscardMotion.cjs`、`checkStockMotion.cjs`、`checkRecycleMotion.cjs`、`checkScreenLayout.cjs`、`checkCardSceneReduced.cjs` を関連範囲に応じて利用・更新する。演出ありと動きを減らす設定を確認し、時間短縮だけでなく最終状態と後続処理を検証する。

実装の終了草案前に `npm.cmd test` と `npm.cmd run build` を実行し、対象検証を含めコマンド・結果を実装報告に記録する。
