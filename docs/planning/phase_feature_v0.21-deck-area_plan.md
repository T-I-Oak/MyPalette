# デッキエリアの正式UI化 開発計画

## 合意内容

- 開発対象はデッキエリアの正式UI化とする。
- 予定バージョンは `0.21.0`、ブランチは `feature/v0.21-deck-area`。
- オーナーから「表示内容や演出内容は、私と調整しながら進める」と指定されている。表示・操作・演出の詳細を計画段階で確定しない。
- 最初に提示した裏面の山、厚み・揺らぎ、枚数表示、専用操作なし、ドロー途中の表返しは候補であり、承認済みの詳細仕様として扱わない。

## 開発スコープ

- レイアウトA/Bのデッキ仮UIを正式UIへ置き換える。
- デッキの表示と残り枚数を既存のゲーム状態へ接続する。
- 初日のストックAからデッキへの7枚配分を正式UIへ接続する。
- 正式エリア同士となるデッキから手札への日次・効果ドロー演出を扱う。
- 山札不足時の捨て札再構成とドロー継続、両方が不足した場合を、既存ルールどおり表示へ反映する。
- 上記に必要なゲーム側の仕様書・開発文書・検証を更新する。

## 対象外

- 捨て札・情報表示エリアの正式化。
- 仮エリアである捨て札からデッキへの移動演出。
- EUI-12全体の正式化。効果発生元の提示、引けない場合の専用通知等はこの計画で一括完了にしない。
- その他のEUI、長押し6面確認、アイコン説明改善、QA-01、追加要素。
- ゲームルール、保存済みカード設定、共通リポジトリの変更。
- オーナー許可のない要求仕様の変更。

## オーナーとの調整手順

1. 実装前に、表示する情報、配置、外観、必要な操作の具体案を提示して確認する。
2. 表示部分を小さな単位で確認可能にし、操作手順・観察点・確認バージョンを提示する。判断とフィードバックを記録し、反映後に再確認する。
3. 初日の受け入れとドロー、通常・不足時のドローについて、順序、表裏、枚数の更新、速度、パネル非表示時の扱いを相談してから実装する。まとまりごとに確認を得て次へ進む。
4. 実装結果の一括確認だけで済ませない。必要な確認には一意のIDを付け、実装報告へ判断・対応・明示的な保留を記録する。
5. 合意した開発スコープ、予定バージョン、ブランチ名を変更する場合は再合意を得る。

## 完了条件

- オーナーと調整した表示・操作・演出が正式UIに反映され、必要な確認結果が記録されている。
- 開始前0枚、初日の7枚配分と4枚ドロー、通常の日次ドロー、効果ドローで、表示とゲーム状態が一致する。
- 山札不足時は捨て札を再構成してドローを継続し、引けるカードがない場合も枚数・手札が正しく表示される。
- デッキ内およびストック・手札との演出で、二重表示、カードの残留、操作競合が発生しない。
- A/B、パネル開閉、リサイズ、エリア固定倍率変更、動きを減らす設定に対応する。閉じたパネルの移動位置・可視性は相談した仕様で検証する。
- 手札・プレイ・パレット・ストックと、仕事開始から物理ロール・後続効果への進行を壊さない。
- 対象テスト、全テスト、本番ビルドのコマンドと結果、必要なブラウザー検証を実装報告に記録する。
- 未回答の必須確認や未対応のフィードバックを残して終了草案を提示しない。保留はオーナーが明示した項目だけとする。

## 実装方針

- `src/game/layoutPresentation.js` の仮デッキ表示をエリア専用presentationへ委譲する。既存のCard裏面、手札、ストックと表現・寸法契約を合わせる。
- `src/ui/screenLayout/` の描画寸法と固定倍率層を使用し、標準描画寸法・オフセットは確定した表示内容から決める。
- 移動には既存のエリア間移動基盤・座標変換を使用する。初日の受け入れ位置・枚数表示について `stockEffects.js` の仮デッキへの依存を解消する。
- ゲーム状態の前後比較だけでは、初日のストック→デッキ→手札や再構成を挟むドローの途中状態を復元できない場合がある。実装前に確認し、必要ならゲーム側に移動記録を設ける。抽選やルール処理を表示側で再実行しない。
- 複雑な演出計画・状態管理は実装前にテストで定義する。演出後の物理ロール・選択待ち・後続効果への再開と、取消・再プレイ時の解放を確認する。
- バージョン設定は初回の実装開始時に `0.21.0` へ更新する。計画段階では変更しない。

## 検証方針

- 単体・結合検証は対応する `tests/implementation/game/` と既存のゲームルール受入テストを利用する。追加検証は移動順序・枚数・再構成・中断等の実際の失敗を検出するものに絞る。
- ブラウザー検証は `scripts/` に置き、外部Playwrightを既存の環境変数で利用する。必須依存には追加しない。
- 初日、通常、複数枚、デッキ途中枯渇、再構成後も不足、両山0枚を確認する。カードのID・ステップ・枚数を実状態と照合する。
- 演出あり／動きを減らす設定、レイアウトA/Bと閉じたパネル、演出中のリサイズ・開閉・固定倍率変更、再プレイで確認する。
- デッキ表示、初日配分、手札配置、ストック交換、仕事開始とダイスロールの既存検証を影響に応じて実行する。
- 実装終了草案前に `npm.cmd test` と `npm.cmd run build` を実行する。失敗は原因・今回との関係・対応を記録する。
