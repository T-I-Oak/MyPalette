# v0.30 定期見直し計画

## 合意内容

- ブランチ: `refactor/v0.30-periodic-review`
- 予定バージョン: `0.30.0`。実装開始時にpackage.jsonとpackage-lock.jsonを更新する。計画段階では現行の0.29.4を維持する。
- オーナーは計画フェーズ開始と、以下の開発内容・予定バージョン・ブランチ名にそれぞれ合意済み。
- Minorの下1桁が0となる新規開発のため、共通ワークフローの定期見直しを行う。

## スコープ

1. 共通規約とプロジェクト固有の開発規定を読み直し、構成・実装・運用との整合を確認する。
2. docs配下の文書について、現在存在しない仕様、章構成、参照先、現行実装との不整合を点検する。
3. 文書の挙動と既存テストの対象、ソースと実装テストの責務・配置の対応を確認する。
4. src、scripts、構成ファイルを対象に、未使用コード、文書との整合性、共通コーディング基準に照らしたファイルサイズと責務を点検する。
5. バックログの依存関係・優先順、オーナー検証項目の判定単位と記録を確認する。
6. 見つかった文書の不整合、未使用コード、動作を維持するソース整理を修正対象とする。

## 対象外

- 新機能、ゲームルール・UI仕様の変更、既存バックログの機能開発。
- QA-01全体の実施。対象要求すべてのassert対応表作成と実機検証はこの見直しに含めない。
- GameWorksOAK共通リポジトリの編集。必要な共通部変更はオーナーへ報告する。
- オーナー管理のdocs/requirements配下の変更。変更が必要なら理由を提示して許可を得る。
- 範囲外の不具合修正。要求・再現条件・期待結果を確認できる範囲でバックログへ記録する。

## 完了条件

- 上記5領域について、確認した範囲、結果、修正内容を実装報告に記録する。未点検の範囲があれば明記する。
- 修正がゲームの動作・仕様を維持することを確認し、範囲外の問題はバックログに記録する。
- ソースの分割・移動を行った場合は、テストの責務と配置、参照文書も追従させる。
- 必要なオーナー検証は一意のID、理由、手順、期待結果、確認バージョンを提示し、判断・対応を記録する。未回答を保留扱いにしない。
- 対象テスト・全テスト・本番ビルドのコマンドと結果を実装報告に記録する。失敗は原因と今回修正するかの判断を記録し、今回の変更に起因するものは修正する。

## 実装方針

- 共通の文書・コーディング・CSS・操作・モバイル・ライブラリ規約を、該当箇所の点検時に参照する。
- 文書のリンクと実装参照、export/import、呼び出し元、ファイル規模を調べ、削除や分割の根拠を確認してから変更する。
- 規模だけを理由に機械的な分割をせず、共通基準と責務に基づいて判断する。
- 未使用コードの判断では、開発者画面、ブラウザー検証スクリプト、本番入口、共通ライブラリ経由の利用も確認する。
- スコープ・予定バージョン・ブランチ名の変更が必要なら、変更案を提示し再合意を得る。

## 検証方針

- 変更したモジュールに対応する既存テストを随時実行する。複雑なロジックを変更する場合は共通規約に従って先にテストで挙動を定義する。
- UIに関係する整理を行った場合は、該当する既存のscripts/check*.cjsによるブラウザー検証を選び、利用可能な実行環境と結果を記録する。
- 文書の参照先、移動後のimport、削除対象の残存参照を再確認する。
- 実装の終了草案提示前に、文書のみの変更でも `npm.cmd test` と `npm.cmd run build` を実行する。
- 実装報告は `docs/planning/phase_refactor_v0.30-periodic-review_implementation.md` に保存する。
- フェーズの引継ぎは共通のフェーズ作業手順に従い、承認された草案だけをphase_handover.mdに保存する。
