# v0.15 プレイエリア正式版UI 開発計画

## 合意した開発内容

- スコープは「プレイエリアの正式版UIの完成」。
- スコープ外は「エリアをまたぐ演出」。
- 目標・効果は常時表示する。
- 細かな配置・外観・操作・演出は計画時に確定せず、実装時にオーナーと相談しながら調整する。勝手に作業を進めない。
- 予定バージョンは0.15.0、開発ブランチはfeature/v0.15-play-area。
- バージョン設定は初回の実装開始時に更新する。計画時は0.14.0を維持する。

## 開発範囲

プレイヤー向け入口のプレイエリアにある評価用の仮表示を、正式なゲームUIへ置き換える。見た目の試作で終えず、制作中の作品の表示・情報確認・操作と、制作段階の進行・完成・出荷を既存ゲーム状態へ接続する。

要求仕様に基づき、厚みと質感のあるキャンバス、現在ステップの絵画、傾斜したイーゼルによる支持・固定、見やすい向き、複数作品の識別と配置、微小な配置の揺らぎを扱う。扇形配置は要求仕様上の希望として検討し、確定方式として扱わない。

目標・効果の常時表示、現在ステップの識別、各ステップの情報確認、達成可能状態、使用するダイスの確認と任意の達成操作、効果の選択待ち、状態変化の表示を完成させる。プレイエリア内の表現・演出も範囲に含め、静止表示だけに限定しない。

エリアをまたぐ移動の演出は今回追加・調整しない。着手・出荷・仕事終了などの領域変更はゲーム状態と表示へ反映する。演出の対象外を理由に必要な状態更新を省略しない。

他エリアとの接続や共通表示部品の必要な変更は、プレイエリアを完成させる目的に沿って扱う。要求仕様、ゲームルール、GameWorksOAKの共通部は独断で変更しない。

## 実装時の相談方法

1. 実装の最初に、着手する具体的な部分と確認可能になる内容を提示し、合意を得る。
2. 合意した部分を確認可能な状態まで作り、オーナーへ見た目・操作を提示して止める。
3. フィードバックを受けて調整する。次の部分の設計・実装へ独断で進まない。
4. 相談と確認を繰り返して正式版UIを完成させる。途中の表示確認を開発全体の完了承認と解釈しない。

キャンバスとイーゼルの具体的な描画方式、作品数が多い場合の配置・閲覧方法、常時表示する情報の構成、詳細確認と達成操作の関係、エリア内演出の内容とタイミングは実装時の相談事項とする。過去に提案した横スクロール、具体的なボタン配置、常時表示する効果の内訳は未合意であり、既定事項として実装しない。

## 完了条件

- プレイエリアが正式版UIへ置き換わり、外観・配置・操作・エリア内演出についてオーナーの確認と調整が完了している。
- 制作中の作品をキャンバスとイーゼルで表現し、支持・固定部分の隙間や貫通を避け、各作品と現在ステップを識別できる。
- 目標・効果を常時確認でき、必要なカード情報や他ステップもゲーム状態を変えず確認できる。
- 現在の未使用ダイスに基づく達成可能表示が更新され、選択した有効な組合せでのみ達成できる。効果選択待ちなどの操作制約が既存Gameと一致する。
- 着手、段階更新、効果処理、完成・出荷、仕事終了、翌日開始、再プレイの各状態が正しく表示される。
- 作品0点・1点・複数点・収まりきらない点数でも、必要な作品の情報確認と操作ができる。
- レイアウトA/B、リサイズ、縦長画面のパネル開閉、狭い・低い画面と高DPRで表示・操作が成立する。
- 既存の手札UI、他エリアとのゲーム接続、評価用ゲームおよび開発者用ツールの機能を維持する。
- 対象テスト、全テスト、本番ビルド、ブラウザ確認の結果とオーナー検証の判断・対応を実装報告へ記録する。未回答や未対応を独断で保留にしない。

## 実装方針

- 既存のGame・session・達成判定・効果処理を再利用し、ゲームルールを表示側に複製しない。
- layoutPresentationのプレイ用ホストを置換する構成を基本に、責務に応じた表示部品へ分割する。Card、共通アイコン、既存画像の再利用を検討する。
- ScreenLayoutから渡される論理寸法と倍率、固定倍率層、共通座標変換を利用する。リサイズやパネル操作でゲーム状態・選択を変えない。
- 再描画・再プレイ・破棄時に監視、イベント、描画資源、演出を解放する。エリア内演出は二重表示や操作競合を避け、動きを減らす設定も扱う。
- 確定した配置・操作・表示契約はdocs/specへ記録する。要求仕様の編集はオーナーの許可がある場合だけ行う。

## 検証方針

- 複雑な配置計算・状態管理には実装前にテストを作成し、純粋な計算とゲーム接続を分けて確認する。
- tests/implementation/game/、tests/implementation/ui/および対応するtests/spec/を対象に、作品数、現在ステップ、達成判定、操作制約、更新と破棄を検証する。
- ブラウザでキャンバス・イーゼルの外観、情報の可読性、全作品へのアクセス、目標・効果の常時表示、達成、効果選択、出荷、再プレイを確認する。既存の画面・ゲーム接続検証も変更の影響に応じて使用する。
- 表示確認用の設定や状態は保存済みカード設定と分離し、本番に検証専用APIを追加しない。
- 実装の終了草案を提示する前にnpm.cmd testとnpm.cmd run buildを実行し、コマンド・結果・失敗時の調査を記録する。
- オーナー検証は確認できる実装ができた時点で項目ごとのID、理由、手順、期待結果、実際の確認バージョンを添えて提示し、判断と対応を記録する。
