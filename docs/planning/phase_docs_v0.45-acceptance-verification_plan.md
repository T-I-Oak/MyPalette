# QA-01 要求02〜05と検証の対応確定 計画

- 対象項目: [バックログ](backlog.md)のQA-01。
- 予定バージョン: `0.45.0`。実装開始時に`package.json`と`package-lock.json`を更新する。
- ブランチ: `docs/v0.45-acceptance-verification`。
- 成果物: `docs/planning/phase_docs_v0.45-acceptance-verification_implementation.md`。
- 対応表・補助資料・証跡は開発成果物として実装報告と`docs/planning/phase_docs_v0.45-acceptance-verification_evidence/`へ置く。オーナー指示により実装仕様とは分離する。

## 目的と対象

要求と検証の関係を条件単位で追跡できるようにする。対象の正本はコミット`f2aa7e5f7d823f9f7468ef79e2c1f8fbc3d6c76e`の次の4文書とする。2026-11-27のオーナー指示「最新版のコミットを基準にしてください」により、このコミットを基準とする。

- `docs/requirements/02.visual.md`
- `docs/requirements/03.information_and_interaction.md`
- `docs/requirements/04.effect_conventions.md`
- `docs/requirements/05.icon_presentation.md`

現行の実装・保存済み設定に対して検証する。要求の基準コミットと検証対象のバージョン・コミットを区別して記録する。基準後の要求変更は比較して対象外と明示し、対象を無断で拡張しない。

D01については、変更前・変更後の節全文を提示し、オーナーのokを得た要求02/03 §3.2の文面変更を本フェーズで反映する。D03も第5章全文案への承認後に反映する。要求文書のそれ以外の変更には、個別の文案提示と事前承認を必要とする。

## スコープ

1. 対象文書の全節を一覧化し、本文・箇条書き・表に含まれる条件をそれぞれ特定する。
2. 条件ごとに実装済み・未実装・合否条件を持たない記述へ分類する。部分実装は条件を分ける。
3. 実装済み条件に既存の単体・結合・ブラウザー検証を対応付け、実行する。不足する検証だけ追加する。
4. 自動検証で確認できない条件は、再現可能な手順で手動確認し証跡を記録する。
5. 未実装条件に既存バックログのIDまたは見出しと項目名を対応付ける。
6. 対応表と開発文書の参照、必要な検証スクリプトを整備する。

## 対象外

- 新機能、カード表示の改善、各エリア・効果UIの正式化。
- 要求仕様の変更（D01で承認された要求02/03 §3.2と、D03で承認された要求02第5章を除く）。
- 要求01・06・07、基準コミット後に追加された要求。
- 全操作順・全入力の網羅検証。
- 共通リポジトリの変更、ゲーム設定・効果評価値の調整。

## 対応表と証跡の設計

- 各条件に一意の検証IDを付け、要求ファイル・節・該当文または箇条書き・表の条件を特定する。
- 1行に実装済みと未実装の条件を混在させない。
- 合否条件を持たない目的・説明・調整の許容範囲なども一覧へ割り当て、検証対象としない理由を示す。
- 自動検証はファイル、テスト名またはスクリプト内の検証箇所、該当assert、実行コマンド、結果、確認バージョンを記録する。
- 手動検証は初期データ、画面サイズ、レイアウト、固定倍率、動きの設定などの条件、操作手順、観察対象、期待結果、実行結果、証跡、確認バージョンを記録する。
- 見た目の要求を、DOMの存在や状態値の一致だけで検証済みとしない。必要に応じて表示画像と目視結果を併用する。
- 未実装は対応する既存バックログを示す。同じ要求を別項目へ二重登録しない。
- 文書が肥大化する場合は実装報告の索引から要求文書単位の補助文書へリンクし、全節・全条件を追跡できる構成を維持する。

## 実装・検証方針

1. 基準コミットの4文書を読み、全節と条件の一覧を作成する。
2. 現行ソース、実装仕様、バックログ、既存テスト・`scripts/check*.cjs`のassertを照合する。ファイル名だけで充足を判断しない。
3. 保存済み設定の読込と既存ブラウザー検証の利用可否を確認する。外部Playwrightとブラウザーのパスを実環境で確認し、未確認の利用可否を成功と扱わない。
4. 既存検証で十分なら追加しない。検証スクリプトの版固定など、今回の検証を妨げる問題は範囲を限定して対応する。
5. 表示・操作の条件に応じてA/B、画面サイズ、固定倍率、通常／動きを減らす設定、マウス／タッチの必要な組合せを選び、選択理由と実施条件を記録する。
6. 実機固有の要求をChromiumや合成イベントだけで確認済みとしない。オーナー確認が必要なら、検証ID・理由・手順・期待結果・確認バージョンを提示する。
7. 実装終了草案の前に`npm.cmd test`と`npm.cmd run build`を実行し、コマンド・結果を実装報告へ記録する。

常用サーバーは再起動しない。表示バージョンの不一致は報告し、本番成果物への置換検証を使う場合は通常の開発URL確認と区別する。新たな検証サーバーが必要なら起動・停止とポートを報告し、終了草案前に停止を確認する。

## 完了条件

- 対象4文書の全節・全条件が分類され、未分類がない。
- 実装済みの全条件で自動または手動検証が成功し、上記の記録項目が揃っている。
- 未実装の全条件に既存バックログの対応先がある。
- 検証失敗、対応先のない要求、未回答の判断事項が残っていない。
- 全テストと本番ビルドの結果が実装報告に記録されている。

検証失敗や要求・実装の不一致を発見した場合は、条件・再現手順・期待結果を記録する。機能修正を無断でスコープへ加えない。別項目への分割・移管が必要なら要求・再現条件・期待結果・完了条件を明記し、オーナー判断を得る。単なる「今後対応」への置換や、未回答の保留扱いでQA-01を完了にしない。
