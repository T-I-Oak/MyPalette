# My Palette 開発環境

## 前提

- Node.js 22.12.0以上とnpm 10以上。初期確認環境はNode.js 25.6.1、npm 11.9.0。
- 共通リポジトリ `T-I-Oak/GameWorksOAK` を、このゲームと隣接する `../GameWorksOAK/` に配置する。
- 共通規約は[新規ゲームの環境構築手順](../../GameWorksOAK/docs/common/09.game_setup.md)から参照する。ゲーム側から共通部は編集しない。

## コマンド

ゲームのリポジトリ直下で、一つずつ実行する。

- 依存復元: `npm.cmd ci`
- 開発起動: `npm.cmd run dev`
- 全テスト: `npm.cmd test`
- 本番ビルド: `npm.cmd run build`
- ビルド確認: `npm.cmd run preview`

Viteのbaseは `/MyPalette/`、出力先は `dist/`。
ゲーム本体の入口は `/MyPalette/`。「ゲーム開始」で保存済み設定を読み込んで検証する。失敗時はタイトルの操作案内を確認し、「ゲーム開始」で設定取得から再試行する。ゲーム画面には旧設定エラー表示と「入口へ戻る」を生成しない。初日は中央のDay・名声値表示が通常サイズから拡大し、左上へ戻ってから自動で開始する。翌日は日末の片付け後に同じ表示が中央へ拡大移動し、日付更新後に左上へ戻って自動で開始する。一日の終了はプレイエリア上端中央、ダイス更新はパレット下部の固定倍率層で操作する。捨て札は表向きの山として表示し、見えているカードだけ詳細を確認できる。信用が0になると、その日の日末処理後に仮のゲーム終了画面が表示される。「タイトルへ戻る」から新しいゲームを始められる。開発者用ツールはローカル開発サーバーの `http://127.0.0.1:3000/MyPalette/dev.html` から開く。
3000番ポートが使用中の場合は次の空きポートへ移り、その実URLを開く。
保存APIは同一Originの `/api/card-settings` を使うため、ホストは `127.0.0.1` を使用する。
プレビューではターミナルに表示されたURLの `/MyPalette/` を開く。既存素材は `public/assets/` に保持する。
バージョンは `package.json` を唯一の設定元とし、共通Env Utilityを通して確認画面に表示する。
`src/version.js`が`package.json`を直接importするため、ゲーム本体と開発者画面の表示は開発サーバー起動時の定数に依存しない。更新後はページを再読込して確認する。

## 構成

- `docs/requirements/`: オーナーが管理するゲーム要求仕様。オーナーの許可がある場合だけ変更する。
- `docs/spec/`: 実装仕様・データ構造・開発ツールの仕様。
- `docs/planning/`: バックログと開発フェーズの成果物。
- `src/`: 起動入口、スタイル、共通ライブラリ接続。
- `public/`: 既存画像などの静的素材。
- `scripts/`: 補助スクリプト。
- `tests/spec/`: ゲーム要求仕様の章に対応する受入テスト。
- `tests/implementation/`: 実装に対応するテスト。

## Gitと作業範囲

バージョンは `package.json` で管理し、正系ブランチは `master` とする。
ダイスとイーゼルはゲーム本体のパレット・プレイエリアで確認する。ダイスの単体・群APIは[ダイスコンポーネント仕様](spec/10.dice_component.md)を参照する。
開発者用入口にはカード設定（`#settings`）と共通アイコン確認（`#icons`）だけを置く。ゲームの操作・状態は[ゲームの実装仕様](spec/09.playable_game.md)、設定操作とJSON形式は[カード設定の実装仕様](spec/08.card_editor.md)を参照する。
編集後は「ゲーム設定を保存」でpublic/data/cards.jsonへ保存する。起動時はこの保存済み設定を読み込む。
効果評価のメタデータはdev-data/effect-evaluation.jsonへ別保存する。同じ保存操作で両ファイルを書き込み、設定画面だけが評価メタデータを読み込む。評価設定の取得・保存APIは `/api/effect-evaluation`。本番ビルドにはindex.htmlだけを含める。dev.htmlは開発サーバーでのみ使い、ビルドには含めない。評価メタデータは静的配信対象に含めず、設定取得・保存APIはローカル開発サーバーでのみ利用できる。
JSONダウンロードは行わない。保存操作は127.0.0.1のローカル開発サーバーで利用する。
本番ビルドには保存済みの設定データが含まれる。設定を外部から取り替える場合はpublic/data/cards.jsonを差し替え、ページを再読込する。エディターはPC向けとする。
開発ブランチは計画フェーズでスコープ・バージョン・ブランチ名に合意してから作成する。
フェーズの開始合意・引継ぎ・終了コミットは[フェーズ作業手順](../../GameWorksOAK/docs/common/03.phase_workflow.md)に従う。Minor の下1桁が0になる新規開発では、[共通ワークフロー](../../GameWorksOAK/docs/common/03.workflow_guide.md#定期見直し)に従って定期見直しを行う。
Gitのリモート設定は `git remote -v` で確認する。

## 実機検証用の GitHub Pages

`.github/workflows/deploy.yml`からGameWorksOAKの共通公開ワークフローを呼ぶ。`master`へのpushは正式版`/MyPalette/`、開発ブランチを選んだ手動実行は仮版`/MyPalette/preview/`へ公開する。公開先の入力欄は設けない。仮版は全開発ブランチで共有する1枠である。

共通処理はNode.js 24で`npm ci`・`npm run build`を実行し、`dist/`を`gh-pages`へ反映する。公開済みGameWorksOAK masterをゲームと隣接配置し、`DEPLOY_BASE_PATH`をViteのbaseへ渡す。ローカルの既定baseは`/MyPalette/`。全テスト`npm.cmd test`は公開前に別途実施する。正式版の清掃ではpreviewを保持し、preview更新はpreview配下だけを更新する。詳細は[共通公開手順](../../GameWorksOAK/docs/common/12.preview_deployment.md)を参照する。

previewを公開するときは、共通部の公開状態を確認し、検証済みの途中コミットを開発ブランチへpushする。Actionsの`Deploy to GitHub Pages`→`Run workflow`で開発ブランチを選ぶ。実装中のpreview公開では引継ぎ書を更新せず、masterへのマージ・正式版の更新はレビューの承認手順に従う。

初回の実行で `gh-pages` が作成されたら、[Settings → Pages](https://github.com/T-I-Oak/MyPalette/settings/pages) で Source を **Deploy from a branch**、Branch を **gh-pages**、フォルダーを **/(root)** に設定する。

[Actions](https://github.com/T-I-Oak/MyPalette/actions) で対象コミットの `Deploy to GitHub Pages` と、その成果物を公開する `pages build and deployment` の成功を確認する。公開 URL は Pages 設定に表示される。既定の URL は [https://t-i-oak.github.io/MyPalette/](https://t-i-oak.github.io/MyPalette/)。ゲーム本体は配信された `data/cards.json` を読み込む。カード設定の保存にはローカル開発サーバーを使用する。

仮版URLは[https://t-i-oak.github.io/MyPalette/preview/](https://t-i-oak.github.io/MyPalette/preview/)。`data/project_info.json`の画像・ロゴ・プレイ先は各公開ルートからの相対パスを使い、`data/update_history.json`はv0期間中は空配列とする。ポータル側のプロジェクト一覧にMyPaletteが登録されると、[preview参照](https://t-i-oak.github.io/GameWorksOAK/?preview=on)で仮版の紹介・素材・プレイ先・履歴を確認できる。

公開前後で既存正式版のindexと参照素材が保持されることを確認する。Actionsの対象コミット、共通ワークフローと共通checkoutのコミットID、配置先、成功を記録し、公開URLでもゲーム・開発者画面のバージョン、素材・標準JSONの読込を確認する。ローカルのpreview用ビルド成功だけでは公開確認済みとしない。

1. 実機のブラウザーでデプロイジョブの URL を開き、タイトルに対象バージョンが表示されることを確認する。
2. 「ゲーム開始」から日付演出を経て自動で初日が始まり、初日の手札が配られ、ダイスロールの結果が表示されることを確認する。
3. 実機の機種、ブラウザー、公開 URL、表示バージョン、操作結果を記録する。

## 検証

ストック表示は`checkStockArea.cjs`、初日・朝・日末演出は`checkStockMotion.cjs`、取得・返却操作は`checkStockAcquisition.cjs`、空ストック・連続交換は`checkStockEdgeCases.cjs`で検証する。各スクリプトに開発URLを渡す。取得・空ストック検証は環境変数`MYPALETTE_STOCK_MOTION=1`で演出あり、それ以外は動きを減らす設定を使用する。

オーナー確認で手札交換をすぐ試す場合は`node scripts/createStockReview.cjs`を実行し、開発URLの`tmp_stock_review.html`を開く。ページ内だけですべてのカードの着手時効果を手札交換1回に変える。自動開始を待つ→任意の手札で着手→返却→取得の順に操作する。保存済み設定は変更しない。生成ページはGit追跡・本番ビルド対象外で、再生成できる。導線の確認は`checkStockReview.cjs <確認ページURL>`。

実装の終了草案を提示する前に、全テストと本番ビルドを実行し、コマンドと結果を実装報告に記録する。
ブラウザ確認用の補助スクリプトは `scripts/` に置く。Playwright はこのリポジトリの必須依存に含めない。
達成後のボード操作確認は`node scripts/createBoardLockReview.cjs`でページを生成し、既存開発URLの`dev_board_lock_review.html`を開く。ページ内だけで検証用の達成条件・即時リロール効果を設定する。保存済み設定は変更しない。`node scripts/checkBoardLock.cjs <開発URL>`で通常／動きを減らす・A/B・即時リロール有無を検証する。生成ページはGit追跡・本番ビルド対象外で、開発ブランチの整理時に削除する。
本番プレビューでは `node scripts/checkProductionStartup.cjs <プレビューURL>` でタイトル表示、設定エラー後の再試行、レイアウトA/Bでの翌日・ゲーム終了・再開始を確認する。
開発サーバーでは `node scripts/checkTitleMenu.cjs <開発URL>` でタイトルメニューが1・2・3項目のときの配置と、幅の拡大・縮小への追従を確認する。

ブラウザー入力制御は`node scripts/checkBrowserInteraction.cjs <開発URL>`で、ズーム用イベントのキャンセル、通常touchの維持、連続タップのclick、内部タッチスクロール、ダイスのCSS、画面回転・A/B切替、開発者入口への非適用を確認する。`checkTitleMenu.cjs`はポータル・設定を含むTab／Shift+Tab除外、`checkProductionStartup.cjs`は終了・復帰時のフォーカスも確認する。`checkDiceSelection.cjs`・`checkCardInteraction.cjs`・`checkCardDetail.cjs`はズーム抑止を有効にしたfixtureで操作維持を確認する。

常用サーバーの表示バージョンが設定と一致しない場合は報告し、AI側で再起動しない。`npm.cmd run build`後、環境変数`MYPALETTE_VERIFY_DIST=1`で`checkBrowserInteraction.cjs`と`checkProductionStartup.cjs`を実行すると、既存Originへのページ・静的素材のリクエストをブラウザー内で`dist/`の内容へ置換して本番成果物を検証できる。この指定は検証ブラウザー内だけに作用し、サーバーを起動・変更しない。通常の開発URLの表示確認とは区別して記録する。

iPad Safariではタイトル下端のバージョンが対象版と一致することを確認してから、縦・横のタイトル・プレイ中・終了画面でピンチ／ダブルタップを試す。開始、カード詳細、内部スクロール、ダイス選択・ドラッグ、パネル、終了・復帰・再開始、ポータルリンクも確認する。合成イベントのキャンセルやChromiumでのタッチ検証だけでSafari実機を確認済みとしない。

`checkPaletteArea.cjs` は、初日の開始前とドロー後の両方で、効果説明アイコンを含む操作ボタン・タブがTab対象外であることを確認する。`checkEffectCommonUi.cjs` は説明のホバー・タップ操作と、Enter／Space／Escapeで開閉しないことを確認する。翌日の検証はストック演出・日付演出・自動開始後の操作可能状態を待つ。

### テストの責務と未検証範囲

`tests/implementation/` の単体テストは原則として対応ソースと同じディレクトリ・ファイル名とする。`game/` は進行・各エリアの配置、`game/easel/` は絵画投影、`ui/screenLayout/` は画面配置、`ui/areaTransition/` は移動基盤を扱う。複数モジュールの結合検証（ロール要求・日次開始・多ダイス等）は検証目的の名前を維持する。`game/deckEvents.test.js` はエンジンとセッションの日次配分・ドロー・再構成イベントの結合検証である。`devServer.test.js` はViteと保存APIの結合、`paintingImageSizes.test.js` は素材の寸法検証である。

| 要求仕様 | 現在の主な検証経路 | 残る検証範囲 |
| --- | --- | --- |
| `01.game_rules.md` | `tests/spec/rules_01_game_flow.test.js`、`tests/implementation/game/` | 固定seedの操作列は全操作順・全入力の網羅ではない。 |
| `02.visual.md` | ダイス・カード・ストック・達成演出の `scripts/check*.cjs`、素材寸法テスト | 見た目の全要求に対応する章別受入テストはない。各正式UIのオーナー確認を併用する。 |
| `03.information_and_interaction.md` | ゲーム接続・手札・ダイス選択・ストック取得のブラウザー検証 | 全公開情報・操作に対応する章別受入テストはない。所持ダイスの長押し6面確認、過去記録比較などの未実装範囲はバックログと照合する。 |
| `04.effect_conventions.md`、`05.icon_presentation.md` | `tests/implementation/icons/`、共通アイコン・効果説明のブラウザー検証 | 全効果・全パラメータの視覚要求を自動検証していない。 |
| `06.dice_effects.md`、`07.other_effects.md` | `tests/spec/effects_06_*.test.js`、`effects_07_game_other.test.js` | 論理と保存形式が中心。効果ごとの正式UIはEUI項目で扱う。 |

文書単位の表だけでは個々の要求の検証箇所を追跡できないため、バックログの `QA-01` で対象4文書の要求と検証の対応を確定する。章別テストファイルがないことだけを不足とは判断しない。固定seedの全操作順の網羅や未実装機能の開発はQA-01に含めない。検証スクリプトの成功を要求仕様全体の適合確認とは扱わない。

## 共通アイコンの確認

効果の共通通知・カード説明の本文、ホバー／タップ操作と通知キューは[効果の共通通知と説明](spec/16.effect_common_ui.md)を参照する。ブラウザ検証は `scripts/checkEffectCommonUi.cjs` と `scripts/checkEffectGameConnection.cjs` を使用する。

`/MyPalette/dev.html#icons` で、効果・目標アイコンを1件ずつ比較する。描画APIとレビューIDは [ゲーム共通アイコン](spec/12.shared_icons.md) を参照する。

ゲーム接続のブラウザ確認は `node scripts/checkGameConnection.cjs <開発URL>`。外部Playwrightのパスを `MYPALETTE_PLAYWRIGHT_MODULE`、ブラウザーを `MYPALETTE_BROWSER_CHANNEL` で指定する。レイアウト・開発者用2画面の回帰確認には `scripts/checkScreenLayout.cjs` を使用する。多ダイスの獲得・表示・ロール・破棄は `scripts/checkLargePalette.cjs` で確認する。

捨て札の表示・参照は`checkDiscardArea.cjs`、達成後・日末移動は`checkDiscardMotion.cjs`、デッキ不足時の3段階再構成は`checkRecycleMotion.cjs`で確認する。各スクリプトに開発URLを渡す。
ストックから捨て札への取得、補充との順序、発注後の日末回収は`checkStockDiscardMotion.cjs`で確認する。

実カード45枚の共通管理は[全エリア共通カード表示](spec/18.card_scene.md)を参照する。カード経路の通し検証は`checkCardScene.cjs`、枚数上限・空・固定倍率は`checkCardSceneLimits.cjs`。動きを減らす設定を維持した配置確定・撤去・日末・翌朝・出荷は`checkCardSceneReduced.cjs`。

日次の自動開始は`node scripts/checkDayStart.cjs <開発URL>`で、停止制御なしに確認する。開始前の状態を観察する開発用スクリプトは`scripts/dayStartGate.cjs`で受信モジュールへ待機ラッパーを挿入する。これは検証ドライバー内だけの制御で、正式ソース・本番ビルドには含まれない。

カード操作と独自詳細UIは `node scripts/checkCardInteraction.cjs <開発URL>`（取得3経路・連続取得・プレイ・返却・背面遮断・フォーカス）と `node scripts/checkCardDetail.cjs <開発URL>`（通常ルート・既存選択dialog内・低い画面・ステップ・終了処理）で確認する。表示状態は `.GameCardDetail[data-open="true"]` を使う。

オーナー確認用には `node scripts/createCardInteractionReview.cjs` で `tmp_card_interaction_review.html` を生成する。上部で取得2枚・手札交換・達成を選び、公開カードの面から詳細を開いて操作する。「発注の準備」後は仕事を終了して発注による取得を試せる。確認ページだけの設定を使用し、保存済み設定は更新しない。

### ボードの取得後クローズの検証

`node scripts/checkBoardBehavior.cjs <開発URL>` は縦長Bの自動クローズ、連続取得・交換、手動開閉の優先、選択中のA/B切替を確認する。`MYPALETTE_STOCK_MOTION=1` で演出あり、それ以外は動きを減らす設定を使用する。
オーナー確認ページ `tmp_card_interaction_review.html` は `node scripts/createCardInteractionReview.cjs` で再生成でき、「連続手札交換2回」も選択できる。縦長Bで確認し、各ケースは「最初から確認」で開始する。

閉じたボード内の演出省略は `node scripts/checkBoardMotion.cjs <開発URL>` で確認する。`MYPALETTE_STOCK_MOTION=1` で演出あり、それ以外は動きを減らす設定を使用する。初日配分、公開切替、再構成後のドロー、途中開閉、A/Bと実カード45枚を検証する。
オーナー確認用は `node scripts/createBoardMotionReview.cjs` で `tmp_board_motion_review.html` を生成する。初日を閉状態・開状態で開始し、公開切替と再構成＋ドローをボードの開閉・A/B幅切替で比較する。確認ページ内だけの状態を使用し、保存済み設定は変更しない。導線検証は `node scripts/checkBoardMotionReview.cjs <確認ページURL>`。

### 着手ボタンの追従確認

`node scripts/createHandActionReview.cjs` で `tmp_hand_action_review.html` を生成する。開発URLの同ページを開き、初日ドローと、任意の手札を着手した際の2枚効果ドローを観察する。ページ内だけで着手時効果を置き換え、保存済み設定は変更しない。上部のA/B幅切替・固定倍率は演出中にも操作できる。動きを減らす設定はOSまたはブラウザーの設定で切り替えて再読込し、上部の有効／無効表示を確認する。

自動検証は `node scripts/checkHandActionFollow.cjs <開発URL>`。Playwrightの指定は既存の `MYPALETTE_PLAYWRIGHT_MODULE` を使う。
